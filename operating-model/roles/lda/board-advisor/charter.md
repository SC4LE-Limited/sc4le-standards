# Board Advisor LDA Charter  
© 2026 SC4LE Limited — Federated Governance

---

## Relationship to the SC4LE LDA Role Standard  
This charter is a **contextual extension** of the SC4LE Local Design Authority role defined in:

`/operating-model/roles/lda.md`

The LDA Role Standard defines the **generic responsibilities, decision rights, behaviours, rhythms, and maturity indicators** for all LDAs.

This Board Advisor LDA Charter **inherits** those definitions and adds **advisory‑specific responsibilities, artefacts, rhythms, and CDA alignment rules** required for founder‑facing governance work.

This charter must always remain aligned with the LDA Role Standard and the SC4LE Federated Governance Model.

---

## 1. Purpose  
The Board Advisor Local Design Authority (LDA) applies SC4LE principles, governance patterns, flow diagnostics, and maturity insights within founder‑facing advisory contexts.

Its purpose is to:

- deliver clarity, decision velocity, and flow restoration  
- translate SC4LE standards into simple, actionable guidance  
- sense real‑world patterns and feed them back into the CDA  
- maintain alignment with the SC4LE Golden Source  
- demonstrate SC4LE through advisory practice  
- support founders in making principle‑aligned decisions  
- reduce decision latency and leadership misalignment  

The Board Advisor LDA is a governed extension of SC4LE, not an independent service.

---

## 2. Scope  

### 2.1 Advisory Activities  
The Board Advisor LDA performs:

- Leadership alignment diagnostics  
- Decision velocity diagnostics  
- Flow and operating rhythm diagnostics  
- Board‑level advisory and strategic counsel  
- Founder‑facing clarity sessions  
- Governance and decision pathway design  
- Operating model interpretation and capability uplift  
- Consequence‑led narrative framing  
- Risk, dependency, and friction identification  

### 2.2 Artefact Production  
The LDA produces governed artefacts including:

- clarity maps  
- decision pathway maps  
- flow maps  
- governance patterns  
- maturity indicators  
- JTBD statements  
- founder‑friendly narratives  
- board‑ready reports  
- diagnostic templates  
- operating rhythm guidance  
- 90‑day recovery plans  

### 2.3 Feedback Loops  
The LDA must:

- log insights into GitHub  
- create issues for new patterns  
- propose pull requests for improvements  
- update diagnostic templates  
- update JTBD lines  
- update founder narratives  
- update visual models  
- update maturity indicators

## 3. Principles  

### 3.1 CDA Alignment  
All advisory work must be grounded in the SC4LE CDA:

- SC4LE Principles  
- Governance Patterns  
- Maturity Model  
- Flow Diagnostics  
- Decision Pathways  
- Operating Model Standards  

### 3.2 Founder‑Friendly Expression  
All SC4LE concepts must be translated into:

- consequences  
- pains  
- jobs‑to‑be‑done  
- simple narratives  
- clear decisions  
- actionable diagnostics  

### 3.3 Version Integrity  
Every advisory artefact must reference:

- SC4LE version  
- artefact version  
- last updated date  
- owner  

### 3.4 Evidence‑Based Advisory  
Advice must be grounded in:

- SC4LE principles  
- diagnostic evidence  
- flow patterns  
- governance signals  
- maturity indicators  

Not intuition alone.

### 3.5 Capability Over Dependency  
The LDA must build capability, not reliance.

### 3.6 Federated Governance  
The LDA must adapt SC4LE to local founder context **without violating principles**.

### 3.7 Continuous Improvement  
Insights from advisory work must be fed back into the CDA to strengthen SC4LE.

## 5. Governance Model  

### 5.1 Authority  
The CDA is the single source of truth.  
The LDA is an adaptive expression of the CDA.

### 5.2 Decision Rights  
The LDA may:

- adapt language  
- adapt examples  
- adapt narratives  
- adapt JTBD framing  
- adapt diagnostic delivery  

The LDA may **not**:

- change SC4LE principles  
- change governance patterns  
- change maturity model  
- change flow diagnostics  
- change operating model standards  

Without CDA approval.

### 5.3 Versioning  
All artefacts must include:

- version number  
- last updated date  
- owner  
- review cadence  

### 5.4 Change Control  
Changes to SC4LE standards must be made via:

- GitHub issues  
- GitHub pull requests  
- CDA review  
- CDA approval
